# HEIC Wasm 디코더 비교 실험

한 장 측정에서 HEIC 처리에 약 1.15~~1.20초, JPEG 생성에 약 33~~35ms가 걸렸다.
실제 Performance trace에서도 HEIC Worker의 픽셀 디코딩이 약 1초를 차지했다.
그래서 Canvas를 다른 곳으로 옮기기 전에 HEIC 디코더를 교체해 비교한다.
속도 개선 정도는 사진과 실행 환경에 따라 달라지므로 같은 조건에서 비교해야 한다.

## 무엇이 바뀌나?

- 기존: `heic-to`에 포함된 JavaScript 디코더와 내부 Worker 사용.
- 실험: `libheif-js@1.23.2`의 Wasm 디코더를 전용 Worker에서 사용.
- 그대로: 최대 두 장 동시 처리, 화면 근처 사진 우선 처리, 원본 RGBA 디코딩,
  메인 스레드에서 260px 중앙 자르기와 JPEG 품질 0.85 적용, 업로드 원본 보존.

Wasm이 작은 크기로 디코딩하는 것은 아니다. 원본 크기의 픽셀 메모리는 여전히 필요하다.
두 라이브러리의 디코더 버전도 같다고 보장할 수 없으므로, 결과는 두 구현의 비교이지
Wasm이라는 실행 방식만의 효과를 완벽히 분리한 실험은 아니다.

## 디코더 선택

실행 중인 개발 서버를 종료한 뒤 아래 둘 중 하나로 다시 시작한다.

```sh
# 기존 JS 방식
NEXT_PUBLIC_HEIC_PREVIEW_DECODER=js npm run dev

# Wasm 실험
NEXT_PUBLIC_HEIC_PREVIEW_DECODER=wasm npm run dev
```

변수를 바꾸면 서버 재시작과 페이지 새로고침이 필요하다.
변수를 지정하지 않으면 개발환경은 Wasm, 배포 빌드와 테스트는 기존 JS를 사용한다.
배포 기본값 변경은 실제 사진 측정 후 별도로 결정한다.

시간 측정용 임시 Console 코드와 관련 테스트는 측정 완료 후 제거했다.

## 오류와 자원 정리

- 사진별 디코딩 후 이미지 핸들과 libheif 컨텍스트를 해제한다.
- 삭제된 사진의 실행 중 디코딩은 끝까지 기다려 동시 처리 제한을 유지한다.
  이후 결과를 버리고, 이미 생성된 Bitmap은 닫는다.
- Worker 실행 오류나 60초 응답 제한에 걸리면 Worker를 종료하고 대기 요청을 실패 처리한다.
  다음 요청은 새 Worker를 만든다.
- 실험 결과가 섞이지 않도록 실패 시 JS 디코더로 자동 전환하지 않는다.
  기존 화면의 미리보기 실패 처리를 사용한다.
