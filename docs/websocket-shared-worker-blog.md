# 여행 탭을 4개 열면 웹소켓도 4개가 필요할까?

여담에서 친구와 같은 여행을 편집하면, 한 사람이 이름을 바꿨을 때 다른 사람의 화면에도 새 이름이 보여야 한다. 변경 알림, 저장 결과, 누가 편집 중인지 같은 정보는 웹소켓으로 주고받는다.

기존 코드에서는 로그인한 탭마다 웹소켓을 열었다. 한 사람이 여행 수정 화면을 두 창에 나란히 띄우면, 같은 브라우저에서 서버로 연결이 두 개 열리는 구조다. 서버는 연결마다 세션을 유지하고 메시지를 전달해야 한다. 그래서 탭이 같은 연결을 나눠 쓰면 서버가 유지할 연결 수를 줄일 수 있다고 봤다.

계기는 토스증권의 SLASH 24 발표였다. 여담에서도 여러 탭 사용이 흔한지는 아직 모른다. 우선 한 사람이 여러 창을 열었을 때 연결을 줄이면서 저장과 알림이 계속 동작하는지 확인하기로 했다. [토스 SLASH 24 발표](https://toss.im/slash-24/sessions/13)

## 어떤 탭의 연결을 끊을까?

**1차에서는 선택한 창만 연결하도록 했다.** 두 창이 나란히 떠 있어도 클릭한 창 하나만 연결을 유지한다. 구조는 단순하지만, 옆에 보이는 창이 실시간 알림을 받을 수 없고 창을 번갈아 클릭할 때마다 재연결이 생길 수 있다.

**2차에서는 화면에 보이는 창은 연결을 유지하도록 했다.** 한 창에서 다른 탭 뒤에 가려진 페이지의 연결은 끊을 수 있고, 나란히 띄운 두 창은 계속 알림을 받을 수 있다. 다만 두 창이 모두 보이면 연결도 두 개다. 저장을 누른 직후 탭을 숨겼을 때, 나중에 돌아와 저장 결과를 확인할 수 있는지도 따로 검증해야 한다.

두 가지를 구현해 보니, 연결을 끊을 탭을 고르는 방식은 창을 어떻게 배치하느냐에 따라 효과가 달라졌다. 그래서 세 번째 실험에서는 탭마다 연결을 열던 구조를 바꿨다.

## 여러 탭이 하나의 연결을 쓰게 하기

여담은 이미 HEIC 미리보기 변환에 **Dedicated Worker**를 쓴다. 각 탭이 사진 변환을 자기 워커에 맡겨 화면이 멈추는 일을 줄이는 데 썼다. 이번에 쓴 **SharedWorker**는 같은 브라우저에서 같은 사이트를 연 여러 탭이 공유할 수 있다. 여기에 STOMP 웹소켓을 한 번 열고, 각 탭은 워커에 메시지를 보내도록 구성했다.

```text
기존          창 A ── 웹소켓 ── 서버
              창 B ── 웹소켓 ── 서버

연결 공유     창 A ─┐
                    ├── SharedWorker ── 웹소켓 ── 서버
              창 B ─┘
```

같은 여행을 보는 탭에는 변경 소식을 함께 전달하고, 저장 결과는 `requestId`로 구분해 저장을 요청한 탭에 돌려준다. 같은 여행을 두 탭에서 편집하더라도, 한 탭을 닫았다는 이유로 편집 중 표시가 사라지지 않도록 마지막 탭이 떠날 때 퇴장 처리한다.

연결을 공유하면서 처리할 일도 생겼다. Turbopack에서 워커 파일이 그대로 출력되어 실행할 수 없던 문제는, 워커를 별도 JavaScript 파일로 번들링해 해결했다. 워커를 지원하지 않거나 시작에 실패하면 기존 탭별 연결로 돌아간다. 탭을 닫을 때는 워커가 그 탭의 통신 포트를 정리하고, 닫힘 알림이 빠졌을 때는 일정 시간 응답이 없는 포트를 정리하도록 했다.

## 모의 서버에서 연결 수를 재봤다

Chrome을 모의 STOMP 서버에 연결하고, 같은 계정으로 탭을 1개, 2개, 4개씩 열었다. 조건마다 5회 반복했고 동시에 열려 있는 서비스 웹소켓만 셌다.

| 열린 탭 | 탭마다 연결 | SharedWorker로 연결 공유 |
| --- | ---: | ---: |
| 1개 | 1개 | 1개 |
| 2개 | 2개 | 1개 |
| 4개 | 4개 | 1개 |

같은 환경에서 한 탭을 남기고 다른 탭을 20번 열고 닫은 뒤에도, 남은 탭이 저장 응답과 변경 이벤트를 받았다. 연결을 강제로 끊었다가 다시 붙는 것도 확인했다. 이 실험에서 잰 수치는 **동시에 열린 연결 수**다. 실제 서버의 CPU·메모리 사용량이나 화면 반영 시간은 아직 측정하지 않았다.

## 실제 백엔드에서 남은 확인

로컬에서 로그인과 여행 조회는 되는데 웹소켓은 열리지 않았다. 여담은 일반 API 서버와 웹소켓 서버를 따로 실행한다. API 서버를 켠 상태에서도 웹소켓 서버가 꺼져 있으면 실시간 연결은 실패한다. 두 서버를 실행한 뒤에는 웹소켓 연결 요청이 `503`을 반환했다. 웹소켓 서버가 API 서버에 로그인 확인을 요청할 때 쓰는 내부 인증 토큰이 실행 환경에 빠져 있었다. Chrome에서 `101`이 보이더라도 `hmr` 행은 개발용 연결이라 서비스의 `/api/ws` 요청과 구분해야 했다. [백엔드 구조와 실행 안내](https://github.com/100-hours-a-week/KTB4-2nd-BE#백엔드-구조)

실제 백엔드에서는 두 서버에 같은 토큰을 적용한 뒤 `/api/ws`의 연결과 STOMP `CONNECTED` 응답부터 확인할 계획이다. 그다음 두 창을 10번 오갈 때 새 연결이 얼마나 생기는지, 협업자가 저장한 이름이 각 창에 뜨기까지 얼마나 걸리는지, 저장이나 갱신이 빠지는 경우가 있는지 비교하려 한다. 실제로 같은 브라우저에서 여러 탭을 함께 쓰는 빈도까지 확인하면, 연결을 공유하기 위해 추가한 코드가 여담에 필요한지 판단할 수 있다.
